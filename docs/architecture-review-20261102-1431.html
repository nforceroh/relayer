1 · Make the store seam real with a shared contract

Strong ports & adapters

app/store.py (RecipientStore, InMemoryRecipientStore) · app/db.py (MySQLRecipientStore) · tests/

Before — two adapters, one tested

flowchart TD
  P[RecipientStore Protocol] --> M[MySQLRecipientStore]
  P --> I[InMemoryRecipientStore]
  I --> T[tests exercise this one]
  M -.never executed by any test.-> X[❌ drift invisible]
  classDef leak stroke:#dc2626,stroke-width:2px;
  class M,X leak

After — one contract, both adapters

RecipientStoreContract: normalize · upsert · order · toggle · delete

InMemory adapter

runs in CI, every test

MySQL adapter

same assertions, against a real DB

Problem: the store seam is only half real. Two adapters exist, so the seam is justified — but only the InMemory one is ever executed. The MySQL adapter's normalization, upsert, ordering, and toggle semantics can drift from the in-memory fake with nothing to catch it, and today they already differ in one place: MySQL orders a single-mailbox query by recipient while the fake always sorts by (mailbox, recipient).

Solution: write the store's behavioural contract once as a reusable test mixin (normalize on write, upsert-on-duplicate, ordering, toggle, delete). Run it against InMemoryRecipientStore always, and against MySQLRecipientStore when a test database is available.

  • the interface becomes the test surface
  • adapter drift fails a test, not production
  • leverage: one contract, both adapters

2 · Test the mailbox directory's selection rule

Worth exploring in-process

app/mailbox_directory.py (30 lines) · tests/

Before — the rule lives only in its docstring

unknown mailbox → first mailbox: untested
empty directory → selected "": untested
grouping order: only hit indirectly

After — the module's own test file

test_mailbox_directory.py

grouping · fallback to first · empty · explicit selection

4 tests against a pure function, no app needed

Problem: build_view owns the UI's selection rule — the fallback from an unknown mailbox to the first one — and nothing tests it directly. It is currently exercised only through route tests that never request a nonexistent mailbox, so the fallback path has no coverage at all.

Solution: a small test_mailbox_directory.py: grouping preserves order, an explicit mailbox wins, an unknown mailbox falls back to the first, and an empty directory selects nothing.

  • locality: the rule is pinned where it lives
  • pure function, no fixtures needed
  • interface is the test surface

3 · Put route tests in the route test file

Speculative in-process

tests/test_mailer.py (326 lines) · tests/test_web_ui.py (97 lines)

Before — a route test living in the mailer file

test_mailer.py: 5 classes, 22 tests, 326 lines
└ RouteWiringTests asserts /ingest wiring — a route concern

After — each file is one layer

test_mailer.py: pipeline + composition only

test_web_ui.py: routes, template rendering, ingest wiring

find a test by the layer it protects

Problem: RouteWiringTests verifies the /ingest route's transport wiring but lives in the mailer test file, so a reader hunting route coverage looks in the wrong file. It was placed there because the bug it guards was a mailer bug — but the thing it asserts is a route's responsibility.

Solution: move it to test_web_ui.py alongside the other route tests; the mailer test file keeps only pipeline and composition.

  • locality: route tests in the route file
  • test file sizes balance: 326 → ~296, 97 → ~130
Honest caveat: this is organisation, not simplification. It earns its place only because "where does a route test live" is a recurring question in this repo.

Top recommendation

Make the store seam real with a shared contract

Two adapters justify the seam, but only one is ever executed — so the seam is a hypothetical one in practice. A shared contract turns it real and makes adapter drift a failing test. It also forces the MySQL adapter's ordering difference into the open.
