After — one deep interface, injected transport

forwarder.process(raw, recipients) → summary

implementation (hidden)

parse · mailbox resolution · code extraction · forward composition · per-recipient send loop

transport is a parameter: real SMTP in prod, fake in tests

Problem: the forward-composition module is the codebase's real logic — parsing, mailbox resolution, code extraction, message composition — yet it has zero tests, because send() welds smtplib and import-time env reads into the same module as the pure composition code.

Solution: accept the transport as a parameter instead of creating it; move env reads out of module import into the composition entry point. The pure functions already exist — the seam just needs to reach the send loop.

  • locality: forwarding bugs concentrate in one module
  • leverage: one interface, every forwarding behaviour testable
  • two transports = real seam, not hypothetical
  • tests stop needing MailHog or network

2 · One configuration module

Worth exploring in-process

app/main.py (6 reads) · app/mailer.py (3) · app/store.py (5)

Before — env scattered, some frozen at import

main.py: SECRET_KEY, INGEST_TOKEN, ADMIN_*, UI_PROTOTYPE
mailer.py: POSTFIX_* frozen at import time
store.py: DB_* read in factory

After — one interface, one place

config module

reads env once · validates required values · hands typed settings to store, mailer, routes

Problem: fourteen os.environ reads across three modules, some at import time — a missing DB_USER surfaces as a KeyError deep inside a request, not at startup.

Solution: a config module that reads and validates env once at startup and hands typed settings to the store factory, the forwarder, and the routes.

  • locality: config errors surface at startup
  • leverage: one interface for every module's settings
  • deletion test passes: complexity concentrates

3 · Extract the ingest auth gate

Speculative in-process

app/main.py (ingest route, 39 lines)

Before — auth and dispatch interleaved

token-configured check
header compare + 6 debug log fields
parse → lookup → forward

After — decorator like requires_basic_auth

@requires_ingest_token

one place: check, log, reject

ingest route: parse → lookup → forward only

Problem: the ingest route mixes token verification (with verbose debug logging) into the dispatch body; the auth rule can't be tested without posting raw bytes.

Solution: mirror the existing requires_basic_auth decorator pattern with a requires_ingest_token decorator; the route body keeps only forwarding dispatch.

  • locality: auth rule in one decorator
  • matches the existing auth pattern
  • route body reads as dispatch only
Honest caveat: the route works and is tested indirectly through the UI suite's ingest check; this is polish, not friction.

Top recommendation

Deepen the forward-composition module

Forwarding is the product — and it's the only core behaviour with zero tests. The pure functions already exist; the seam just needs to reach the send loop so the whole pipeline becomes testable through one interface.
