Problem: the composition tests cover the plain-text branch, but the HTML branch — the one most real mail takes — is untested: the derived plain-text fallback, the multipart/alternative structure, and the HTML-escaped preamble (an injection surface if it regressed).

Solution: add composition tests: an HTML original produces a forward with both a plain and an HTML part, the preamble escapes sender/mailbox, and the fallback text derives from the HTML when the original had no plain part.

  • locality: injection regressions become testable
  • leverage: existing pure interface, new coverage
  • zero production risk

Problem: 72 of index.html's 102 non-Jinja lines are byte-identical to prototype.html — the sidebar, heading, and recipient-entry structure are copy-pasted, so a layout fix must be made twice.

Solution: extract Jinja macros for the shared structure; each template passes only its action controls (POST forms vs mock attributes) as parameters.

  • locality: layout fixes land once
  • each template reads as its differences only
  • prototype deletion gets cheaper

Problem: the prototype's purpose is spent — variant C won and is production. Keeping it means every future UI change must consider two templates, and ui_prototype threads through config, factory, and tests for a mode nobody previews anymore.

Solution: delete prototype.html, its CSS, the ui_prototype setting, and the template-choice branch; the prototype tests fold into the production suite.

  • deletion test passes: complexity vanishes
  • ~450 lines deleted
  • one UI, one template, one test path
Only you can decide this: the prototype is your preview bench for future UI ideas. If you still want it for the next redesign, keep it; if variant C is the destination, retire it.
